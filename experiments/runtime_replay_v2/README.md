## Что сломалось

В старой S1, `environment__t3_i2`, rollout seed `52320000`, задача:
`pick up the bbq sauce and place it in the basket`.
У H16 и event без вмешательств первые 80 действий совпали точно,
но наблюдения начали расходиться раньше. Эпизоды закончились success
на разных шагах (240 и 237), поэтому строгий audit остановил очередь.

Старый `scripts/libero_runtime_snapshot.py` сохраняет time/qpos/qvel,
ctrl, часть model/controller state. Он не сохраняет `qacc_warmstart`.
При `env.reset()` MuJoCo решает контакты в новом начальном размещении;
остаточный warmstart затем используется при восстановлении другого state.
Равенство только qpos/qvel этого различия не обнаруживает.

Отдельно выявлена проблема soft restore: таймеры и кэш сенсоров robosuite
не восстанавливались. Даже при одинаковой физике они могут выдавать разные
наблюдения. Принудительное обновление сенсора тоже изменяет его часы.

## Как проверили причину

Взяли сохранённые **240 действий H16** и старый start.npz. Модель не загружали,
новых actions не генерировали, GPU не использовали. Меняли seed перед reset;
все последующие actions оставались неизменными. Три повтора каждого режима
проведены локально и на сервере, MuJoCo 3.3.2, robosuite 1.4.0, NumPy 2.2.6.

| Восстановление | Локально | На сервере |
|---|---|---|
| Старое | Траектории расходятся с первого физического шага | То же |
| Полный `sim.reset()` перед старым restore | 3/3 точно одинаковы | 3/3 точно одинаковы |
| Только нулевой warmstart перед старым restore | Совпадает с полным reset, 3/3 | Совпадает с полным reset, 3/3 |

Здесь 3/3 означает, что три полных trace совпадают между собой, а не три
независимых научных эксперимента. Между разными компьютерами битовую
идентичность не требуем. Success на t240 у всех этих open-loop replay не
означает, что ошибка безвредна для замкнутой policy: разные наблюдения
меняют следующие предсказания.

Это воспроизводимый механизм расхождения и сильное объяснение сбоя S1.
**В11:11 МСК closed-loop GPU smoke на проблемном случае прошёл:** H16 и
event имеют одинаковые действия, состояния, query input hashes и видео,
оба заканчиваются наt237. Все6ветвей прошли strict audit. Полные benchmark
серии ещё считаются; это не подтверждение общего SR-эффекта.

Артефакты: [локальная диагностика](local_diagnostic/summary.json),
[warmstart ablation](local_warmstart_ablation/summary.json),
[серверная диагностика](server_diagnostic/summary.json).
`replay.py` сохраняет также численные traces, не только итоговый success.

## Исправление

Новый [runtime_snapshot.py](runtime_snapshot.py) расположен отдельно от
замороженного v1-кода. Основные изменения:

1. Сохраняем `mjSTATE_INTEGRATION` через `mj_getState`, включая warmstart,
   activations, ctrl, внешние силы и прочие inputs, включённые в этот state.
2. Восстанавливаем integration state, вычисляем derived kinematics через
   `mj_forward`, затем возвращаем сохранённые inputs ещё раз: сам forward
   изменяет warmstart. Проверяем точное равенство integration state.
3. Сохраняем sensor clocks, sampled flags, observed values, cache и torques.
   Возвращаем сохранённое наблюдение без лишнего forced sensor update.
4. NPZ работает с `allow_pickle=False`; указаны schema v2, MuJoCo version,
   state specification. Старые snapshots отклоняются, а не «дополняются» нулями.
5. Поддержка явно ограничена используемым OSC без interpolation и сенсорами
   без случайного шума/фильтрации. Это не универсальный snapshot любого робота.

Нулевой warmstart был только диагностической ablation, **не production-fix**.
Нужно сохранять реальное состояние, особенно при ветвлении из середины эпизода.
Это согласуется с документацией MuJoCo о [warmstart и полном integration state](https://mujoco.readthedocs.io/en/latest/programming/simulation.html#state-and-control).

## Проверки

- Реальная CPU-среда: восстановление с t0/48/80/160 и продолжение до t240.
  Проверяются все компоненты integration state, все наблюдения и success
  после каждого действия, а не только финальная позиция.
- Повторы после разных reset seeds и предшествующих траекторий; passive
  monitor каждые четыре действия; hard/soft restore; точный NPZ roundtrip.
- Отказ для старой schema, другой версии MuJoCo и другого state spec.
- Локальные RGB-тесты используют **llvmpipe, CPU-rendering**, обе камеры
  256x256. Это не проверка NVIDIA EGL на сервере.
- Проверки запускателя: сохранение task/init/arms/settings, явный будущий
  deadline, отдельный collector, неизменный strict audit и reporter.

Результаты pytest хранятся рядом как JUnit XML. Политика тестов: точное
`assert_array_equal`; допуски не увеличивали.

Итог выполненных проверок:

| Проверка | Результат |
|---|---|
| CPU simulation + protocol + прежние P3 unit tests, локально | 30 passed |
| Те же проверки на сервере | 30 passed, 52.17 с |
| RGB: initial observation и soft restore | 2 passed |
| RGB: suffix replay с t0, t80 и t160 до t240 | 3 passed, 173.89 с |

Полный RGB-тест сравнивает каждый кадр обеих камер, а не только итоговые
изображения. Ни один из этих тестов не вызывает нейросеть. Источники:
[local CPU](local_final_tests.xml), [обновлённый protocol](protocol_tests.xml),
[server CPU](server_final_tests.xml), [short RGB](local_rgb_tests.xml),
[full RGB replay](local_rgb_full_replay_tests.xml).

## Следующие GPU-серии

Подготовлены entrypoints [collect_v2.py](collect_v2.py) и [run_v2.py](run_v2.py).
Они используют прежний collector, выбор candidates, методы и строгий audit;
заменяют только snapshot module для нового процесса. Root `scripts/*.py`
не изменены. Новые файлы также фиксируются SHA в config каждого запуска.

Порядок, независимо от SR:

1. S0-v2: полный повтор исходной таблицы, все пять arms, 199 случаев.
2. S1-v2: те же задачи/init, rollout seed +10 000 000.
3. S2-v2: rollout seed +20 000 000.

Каждая серия: 995 main + 18 smoke; вместе 3039 rollout. Первым smoke идёт
именно проблемный environment/task3/init2/seed52320000, включая shadow.
Далее два прежних smoke случая. Сначала smoke,
затем main; техническая ошибка останавливает продвижение. Ни один старый
outcome не переносится в v2. Новый SR по v2 пока отсутствует.
Оценка по прежней скорости: около 1.5-2.5 часов на серию при восьми свободных
GPU; 4.5-7.5 часов на все три, без гарантии наличия GPU и без ожидания/дебага.

Старые итоговые counts сохраняются как исторические измерения v1.
Успешный прежний audit не доказывает равенство отсутствовавшего в snapshot
warmstart. Поэтому строгую paired-интерпретацию надо перепроверить в v2;
само обнаружение ошибки не доказывает ни исчезновение, ни усиление P3-эффекта.
Сравнение seeds на одинаковых task/init также требует проверки начальных
hashes; не предполагаем точную изоляцию model noise между группами.

До разрешения пользователя в11:05 GPU-серии не запускались: прежний срок09:00
истёк. Текущий запуск и новый deadline описаны в [протоколе](LAUNCH_20260915.md).
`--prepare` только создаёт configs и не занимает GPU.
Серверные команды из корня проекта:

```bash
.venv-cosmos/bin/python experiments/runtime_replay_v2/run_v2.py --prepare
.venv-cosmos/bin/python experiments/runtime_replay_v2/run_v2.py --launch --deadline "$DEADLINE"
```

`DEADLINE` должен быть будущей ISO-датой со смещением часового пояса.
Запуск с истёкшим/неуказанным сроком отклоняется. GPU0-7 только idle-only,
по одному worker на GPU, с прежними project locks и проверками занятости.
Чужие процессы не останавливаются. Для уже идущей v2 очереди второй запуск
не может переписать бюджет: supervisor защищён отдельным lock.
